# claude-context-dashboard

Local Node.js tool (no dependencies, ESM, built-in `http` only). Run with `node bin/cli.js [--path <dir>] [--port <n>] [--no-open]`.

`npm test` runs both suites against a throwaway `HOME`, so it never touches real config. Run it after ANY change to `src/toggle.js`, `src/scan.js`, `public/app.js` or the API surface: most of its checks exist because something was once wrong, and three rounds of adversarial review each found real defects in freshly written fixes there. Add checks rather than trimming them.

- `test/write-paths.test.mjs` — every write path, plus the coverage list the page shows.
- `test/editor.test.mjs` — the editor and project switcher: `public/app.js` is run in a `vm` context against a real server. The stand-in serves only ids that exist in `public/index.html` and clicks are aimed by parsing the buttons the page actually drew (`buttonsIn`), so a renamed action or a missing element fails here instead of only in a browser. Two things keep that working, so don't undo them casually: `public/app.js` must stay a classic script (a `type="module"` script has no reachable globals, and the test calls `openEditor`/`saveEditor`/`diffRows` through the context's global object), and only top-level `function` declarations are reachable that way — `let`/`const` are not, which is why every check reads elements, requests or files rather than the page's own state.

- `src/scan.js` — read-only inventory of everything that feeds a project's Claude context (CLAUDE.md hierarchy, settings layers, plugins, MCP servers in all three scopes, skills, subagents, hooks). Pure functions, no writes. `buildInventory` is the expensive call (it reads all of `~/.claude.json`), so anything needing both path sets builds one inventory and passes it to `editablePathsFrom`/`viewablePathsFrom` — opening a file in the editor used to build three. It follows two different kinds of layering out of a `CLAUDE.md`, and must keep them apart: `@` lines, whose text Claude Code really loads (`followImports` — every line gets a row, including a dead one, one naming a file that cannot be read, and one an earlier line already pulled in, so a short file with a broken `@` line cannot be mistaken for a short file), and plain mentions of other files in the prose (`followReferences` — a markdown link, a path in backticks, a path written plainly), which Claude Code does NOT load. The second kind is reported separately and never counted as weight; saying otherwise would break the one promise the weight section makes. It is deliberately narrow to stay free of noise: only documentation extensions, only files that exist beside the file naming them (resolving against the project root as well turned the global CLAUDE.md's passing mention of a filename into a claim about this project), and capped by depth and count. It also returns `coverage`: what the scan read and what it did not, built from the same paths and constants the scan uses (`claudeMd.searched`, `skillDirs`/`agentDirs`, `MAX_IMPORT_DEPTH`, `scanSettings`'s `sameFile`) — if you change where the scan looks, that list moves with it, so never restate a path there by hand. Every line in it is a claim the page makes about itself, so it has to hold when a file is unreadable rather than missing, and when one file is reachable under two of the four settings names; and "not read" must mean the scan did not open the file, not that its contents don't reach the conversation.
- `src/toggle.js` — the only module allowed to write to real Claude Code config files. Backs up the target file before writing, writes atomically (temp file + rename) preserving the original file's permission bits, and refuses to write if the file's mtime changed since it was read (another Claude Code session may have written it). Because that rename would replace a symlink with a regular file, `writeTextAtomic` resolves a linked target first (dotfiles repos) — but only to a file with the same extension, so a `settings.json` linked to anything else is refused; `writeEditableFile` still refuses links outright, since it writes arbitrary typed text (except when putting an earlier version back, which is this dashboard's own copy of that same file). Note what this deliberately softens: the exact-path rule below governs which path may be *named*, and following a link then lets that write land anywhere the user's own link points, extension aside. That is the trade, and the README states it. `toggleMcpShared` writes to the settings file that currently decides the server (`explicitlySetIn` on the inventory row) rather than always to `~/.claude.json`, since a settings layer outranks that record — except when that file is a global layer, where it writes the project's own `settings.json` instead, because a per-project switch must never change every project; backups are filed under the path the write resolved to (so a linked file's versions are found under the link's target), `BACKUP_NAME` is the single shape used to find them, to check an id names one, and to prune (the moment in a copy's name only ever moves forward for a given file — `nextBackupPath` clamps above the newest already filed, since which copy is newest is read off the name, and a clock stepping backwards would otherwise file the new copy as the oldest and have it pruned) (an id is a version of a file only if what follows that file's name is a timestamp and nothing else, or every `x.disabled` copy would count as a version of `x`), and `pruneBackups` runs after every copy to hold the folder to 20 per file and 50 MB in all — never dropping a file's newest copy, and with `CLAUDE_DASHBOARD_BACKUP_BUDGET` as a test-only override for that total;  the global/private MCP switches refuse while a name has both a live and a parked definition, and `resolveMcpDuplicate` is how that is settled. `toggleFile` is restricted to known skill/agent directories; every other write goes through `assertEditable`, which allows a path only if `collectEditablePaths` (built from the inventory itself) lists it for that project. A file an `@` line pulls in is on that list — it is instructions text that loads — but only under the exact name the line gives it and with no `.disabled` twin, since switching it off would leave the `@` line pointing at nothing; a file the prose merely names is viewable but NOT editable, and `assertEditable` says that in its own words rather than falling through to the general refusal, which would be a lie about a file the page is showing. That comparison must stay EXACT — matching on the symlink-resolved path would let a symlinked `CLAUDE.md`'s target be named directly and overwritten. The scanner reports paths built from the realpath-resolved home and project root, so exact matching is what the frontend always sends.
- `src/server.js` — plain `http` server bound to `127.0.0.1` only. Serves `public/` statically, exposes `/api/inventory`, `/api/projects`, `/api/file` (read a file back for the editor), `/api/file/backups` (list, or read one, of the backups already taken for that file), and the `/api/toggle/*` + `/api/file/save` + `/api/file/restore` + `/api/restart` POST endpoints. `/api/restart` is the stale-version banner's own button: the process closes the listener, spawns a fresh one from the same command line (with `--no-open` added — the browser is already there), and stays alive waiting for it rather than detaching it, so the launching terminal keeps owning the dashboard and one Ctrl+C still stops it. The work itself is injectable (`createServer(path, port, { onRestart })`) so the suites can watch the endpoint without restarting the test run. Everything that reads or writes an arbitrary file requires a matching Host/Origin, and POSTs additionally require an `application/json` content type (CSRF defense — see `isSameOrigin`).
- `public/` — vanilla HTML/CSS/JS frontend, no build step, no framework.

See [README.md](README.md) for the short public description, and [docs/reference.md](docs/reference.md) for what each section shows and exactly how each toggle mutates config.

Never park dashboard-only state inside a `settings.json` — Claude Code validates that file and warns about unknown keys. Switched-off hooks go in `~/.claude-context-dashboard/parked.json`. (`~/.claude.json` is internal state, not schema-validated, so the shadow keys for switched-off MCP servers live there.)

Schema assumptions (MCP scopes, plugin install records, plugin manifest paths) were reverse-engineered from real files under `~/.claude/` and `~/.claude.json` on 2026-09-06 — if Claude Code changes those formats, `src/scan.js` is where to update. They are written down one by one in [docs/schema-assumptions.md](docs/schema-assumptions.md), numbered, and `bin/check-config.js` verifies that list against whatever machine it is run on (read-only, prints no values or paths, exits 1 on a mismatch). The numbers, the doc and the checker move together: adding an assumption to the code means adding a row and a check, or the README's invitation to report mismatches is checking a list that no longer describes the code.
