# Reference

The long version: exactly what the dashboard reads, what each switch writes, and
what it refuses to do. [README.md](../README.md) is the short version.

## What it shows

- **What loads before you type** — how much each thing actually adds to the conversation at startup, measured in UTF-8 bytes (the size on disk, not a count of characters) with a rough token conversion, broken down by category and listed biggest-first. The measurement is honest about what it counts: an instructions file counts in full, plus everything its `@` lines pull in (followed recursively); a skill or subagent counts only its name and description, because that is all that goes in until one is used; tool connections are **not** counted at all, since measuring the tool list they send would mean connecting to those servers, which this dashboard never does.
- **Instructions files (CLAUDE.md)** — the global one, the project's own, any ancestor folders between them, and any nested ones that would load if you work inside a subfolder. Shows its size, opens whole in the viewer, and lists every file its `@` lines pull in as a row of its own: what the line says, which file that turned out to be, how much text it brings, and one level of indentation per hop, since an imported file can import more. A line that brings nothing gets a row too — the file is not there, it cannot be read, or an earlier line already pulled it in — because a short `CLAUDE.md` whose `@` line is dead looks exactly like one that has nothing to say. Symlinked project paths are resolved to their real location first, so the same project reached two different ways is reported identically.
- **Files the instructions point at** — the other kind of layering: a `CLAUDE.md` that says "read `docs/architecture.md` before touching the parser" instead of `@docs/architecture.md`. Claude Code does not load these, so they are listed apart from the instructions files and **do not count towards the weight** — they arrive only when Claude follows the pointer, which is usually what the wording around them is asking for. The section leads with the total: on a real project a `CLAUDE.md` of a few thousand bytes routinely has ten or twenty times that sitting a pointer away (14,528 bytes loading against 192,863 behind the pointers, in one of mine). Found by reading the instructions text — and the text of anything its `@` lines pull in, which loads just the same — for anything shaped like a path — a markdown link, a path in backticks, a path written plainly — that ends in `.md`, `.markdown`, `.mdx`, `.mdc`, `.txt` or `.rst` and is there on disk beside the file naming it; those files are read for pointers in turn, three levels deep and forty files at most. Anything already pulled in by an `@` line is left out of this list, since it is reported as loaded instead. A path naming a file that isn't there is not listed at all, and neither is a reference to code (a `CLAUDE.md` naming `src/parser.js` is saying where the code lives, not adding a layer of instructions).
- **Files it will not read, and files it could not read.** The scan opens only ordinary files: a device, a pipe or a folder where a file should be is refused (an `@` line naming `/dev/zero` used to hang the server). Text files over 2 MB (instructions files, skills, subagents, memory notes), JSON files over 16 MB (settings, plugin records) and a `~/.claude.json` over 256 MB are not read either; `~/.claude.json` gets the larger limit because it legitimately grows with every project you have opened. A file that cannot be read or is over its limit does not vanish from the page: it is named in a warning at the top, and an `@` line naming one gets a row that says so.
- **Partial warnings.** A file that parses but has the wrong shape in one place — an install record that is not a list, an `enabledMcpjsonServers` that is not an array — is reported as a warning naming the file and the key, and only that part is left out. The rest of the page, the editor included, still works. The shapes the scan expects are in [schema-assumptions.md](schema-assumptions.md).
- **Settings & permissions** — all four `settings.json` / `settings.local.json` layers (global and project), shown separately so you can see exactly which file set what, including the ones that don't exist yet so you can create them. Each setting is shown in words rather than as raw JSON, and permission rules are listed one per line with what each one actually permits ("Run the shell command `git push:*`", "Use the `search_issues` tool from the github connection") next to the exact rule text. Rules can be added and removed one at a time, without rewriting the file. A file that exists but can't be read as settings — bad JSON, or valid JSON that isn't an object, such as a bare `null` — is called out as a warning at the top and ignored, instead of silently being skipped or taking the page down with it; it still opens in the editor, which is where you would go to fix it.
- **Plugins** — every plugin that applies to this project (installed globally, installed just for this project, or both — labeled accordingly), its description, what it contributes (commands/subagents/skills/hooks), and whether it's actually turned on here — accounting for per-project overrides. Plugins named in a settings file but not installed anywhere are listed too, so a setting that quietly does nothing is visible rather than hidden.
- **MCP servers** — split into the three scopes Claude Code actually uses: global (every project), shared via the project's own `.mcp.json`, and private local servers just for you on this project. The shared-server enabled/disabled/undecided state is worked out from every settings layer that can carry it (not just one file), since that approval commonly lives in the project's own `settings.local.json`.
- **Skills** and **Subagents** — global, project-level, and the ones bundled inside enabled plugins.
- **Hooks** — the commands that run automatically around Claude Code's own actions, listed one by one with the command each one runs, and which settings file (or plugin) it came from.
- **Memory** — this environment's own per-project memory files under `~/.claude/projects/<project>/memory/`. Only the index (`MEMORY.md`) is loaded automatically at the start of a session; the notes it links to are read when they turn out to be relevant.
- **What this looked at** — the last section on the page: every file and folder the scan read, and next to it what it did not read and why. It is built from the same paths the scan itself used, so it can't drift into describing a scan that no longer happens. This is where you find out, for instance, that a `CLAUDE.md` more than one folder deep inside the project isn't listed (Claude Code would load it if you worked in that folder), or that a settings file installed for the whole machine — which outranks everything shown here — isn't read at all, and whether one exists.

## How the on/off switches work

- **An undecided "this project" switch** — a plugin that follows the global setting, or a shared MCP server nobody has approved or refused here — is shown by what is happening now, and its first click sends the opposite of that. It used to write the state it was already in first, and only the second click changed anything.
- **Plugins** have two switches: **every project** writes your global `~/.claude/settings.json`, and **this project** writes `<project>/.claude/settings.json`, which overrides the global default. A project that has an override also gets a button to drop it and follow the global setting again. Any switch that changes every project at once asks for confirmation first.
- **MCP servers shared via `.mcp.json`**: toggling uses Claude Code's own per-project enabled/disabled list, the same mechanism Claude Code itself uses. Those lists are ordinary settings keys, so the same server can also be named in any of the four settings layers — and a settings layer outranks `~/.claude.json`'s own record. The switch therefore writes **wherever the decision is currently being made** (the row says which file that is), rather than writing the record and leaving the server exactly as it was — with one exception: if that file is one of the two that apply to *every* project, it is left alone and the answer goes in this project's own `settings.json`, which outranks it here. A switch that says "this project" must not turn a server off everywhere. You're told when that happens, and if the project has no settings file of its own to override with (its `.claude` folder is a link to the global one), the switch is refused with an explanation rather than quietly going global. If something else still decides after the write — a blanket "enable all project MCP servers", say — you're told that too, instead of being shown a switch that lies.
- **Moving a tool connection between the two**: a global connection has a button to use it **only in the project you are viewing**, and a project one has a button to make it available everywhere (which asks first). The definition is carried across exactly as it was — a switched-off connection moves too, and arrives switched on, since moving it somewhere is how you say you want it there. This matters more than it looks: the list of tools a connection sends is usually the single largest thing that enters a conversation at startup, so a connection you only need in one project does not belong in every one.
- **Private, per-project MCP servers** and **global MCP servers**: since there's no built-in "disabled" flag for these, turning one off moves its config into a shadow key in `~/.claude.json` instead of deleting it, so turning it back on restores it exactly. Ones switched off this way stay listed (marked "switched off here") so you can switch them back on. If a server that was switched off here is set up again under the same name by another route — `claude mcp add`, or an edit by hand — there are two real definitions of it, and restoring the saved one would overwrite the new one. So the row shows both, switching and moving it are refused, and you choose which to keep; the one you drop is still in the backup taken before the write. Global servers are labeled clearly because turning one off affects every project, not just the one you're viewing.
- **Skills and subagents** (the ones that aren't bundled inside a plugin): toggling renames `SKILL.md` / `<agent>.md` to add or remove a `.disabled` suffix — Claude Code simply won't see a file it doesn't recognize by name. Skills/subagents that come from a plugin can't be toggled individually; disable the plugin instead.
- **Instructions files and memory notes**: switched off the same way, by renaming. A switched-off file stays listed (marked "switched off") so it can be switched back on, and its content is never touched.
- Renaming never writes over an existing file. If both a live file and a switched-off copy of it are somehow present, switching is refused with both names, rather than reporting success while the live file keeps loading.
- **Hooks**: switching one off moves that hook's definition out of the settings file and into `~/.claude-context-dashboard/parked.json`, so the settings file stays valid against Claude Code's own schema and the hook comes back with its definition untouched, in the slot it occupied when you switched it off. (Switching several hooks for the same event off and back on in a different order can therefore reshuffle them relative to each other.) A toggle carries the hook's exact definition, so if the list has changed since the page was drawn, the right hook is still the one that moves — or you're told to reload. Two hooks in the same event can be written identically; each is treated as a separate hook, so switching both off and back on gives you both. Since that means a definition alone can't identify a hook, the two files are written as a pair: if the second write fails the first is put back, rather than leaving a hook in neither file. Hooks contributed by a plugin can't be switched individually — turn the plugin off instead.

## The page itself

- **Status line.** Every write reports on a line under the top bar (which file, and that a backup was kept), and every refusal appears there too, in place of a browser alert box. It is a live region, so screen readers announce it.
- **Choosing a project.** Typing a path and pressing Enter loads it; the address bar's `?path=` follows the project you are looking at, so a reload or a bookmark returns to it. A path that cannot be loaded shows its error and leaves the page you were on, rather than blanking it.
- **Asking first.** Besides the switches that change every project, two more writes ask: saving a permission rule whose text is not a shape the page can describe (a typo in a tool name, a stray space), and any permission edit that lands in the global settings file.
- **Paths** under your home folder are shown as `~/...`. This is display only; requests still carry the full path.
- The on/off controls are `role="switch"` buttons with their state exposed, keyboard focus returns to the same control after the page redraws, and the editor traps focus while open and gives it back to what opened it.

## Editing files

Every file the dashboard lists opens **in full** in a built-in editor — there are no truncated previews. Instructions files, the files their `@` lines pull in, all four settings layers (including creating one that doesn't exist yet), `.mcp.json`, skills, subagents and memory notes can also be saved back. `Esc` closes the editor, `Cmd`/`Ctrl`+`S` saves. A file that can be read but not written — one belonging to a plugin, or a symlink — opens read-only, with the reason shown and no Save button.

- A file is editable **only if the dashboard is listing it for the open project, spelled exactly as the dashboard listed it**. The exactness matters: matching on the symlink-resolved path instead would mean that an instructions file which is a symlink to, say, `~/.ssh/authorized_keys` would let that target be named directly and overwritten.
- A file that is itself a symlink is read-only **in the editor**. It can still be switched off (that renames the link, not what it points to), but saving typed text over it would replace the link, so you're told to edit the file it points at instead. Switches behave differently — see the paragraph below.
- A file reached through a **linked folder** is a different matter: editing it writes where the folder really points. That is usually what you want — a skills folder symlinked out of a git repo, say — and the dashboard says so on the row. The one case that would be misleading is handled separately: if a project's `.claude` folder is a link to your global one, the two are recognised as the same file and the dashboard stops offering a switch labelled "this project" that would in fact rewrite your global settings.
- Files that belong to an installed plugin are read-only, because a plugin update would silently overwrite the change.
- An `@` line that resolves **outside the project and outside `~/.claude`** — `@~/.bashrc` in a cloned repository's `CLAUDE.md`, say — still loads, so its text is shown and counted and it opens in the viewer, but it is read-only: a project's instructions file does not get to make an arbitrary file of yours editable by naming it.
- A file that an instructions file only **points at** is read-only too, and says so: nothing loads it, so it is an ordinary project document that belongs to your own editor. A file an `@` line **pulls in** is the opposite case — that text really does load — so it can be saved, but only under the exact name the `@` line gives it, and it gets no on/off switch: switching it off would not park it, it would leave the `@` line pointing at nothing.
- A settings or `.mcp.json` write is refused, with the file untouched, when the key it would change holds the wrong kind of thing: adding a permission rule when `permissions.allow` (or `deny`, `ask`) exists but is not an array, or switching a server off or moving it when `mcpServers` is an array or anything but an object. Replacing the value would have kept only the new rule or dropped the definition, leaving the old contents in a backup alone.
- Writes made for a **project** (a project plugin switch, a project's MCP switch, saving one of its files) are refused if the folder they would land in is a link that leads outside the project or into your global `~/.claude` — a repository that ships `.claude -> ~/.claude` would otherwise turn a "this project" switch into a change to every project. This is checked on the folder itself, so it holds when the file inside it is not a link.
- A file whose name ends in `.json` is parsed before being written; if it isn't valid JSON — or is valid JSON that isn't an object, like `null` or a list — you get an error and nothing is saved. Both would break every reader of the file, Claude Code's included.
- Saving is refused if the file changed on disk since the editor opened it (see below for exactly what is compared).
- A refused request comes back as HTTP 400 when the request is the problem (a path not listed, a wrong-shaped key, bad JSON, a read-only file) and 409 when the file changed on disk since it was read; reload and try again.
- Closing the editor, opening another file, switching project or leaving the page with unsaved typing asks first. Only one save runs at a time — a second `Cmd`/`Ctrl`+`S` while the first is still going is ignored rather than sent with a modification time that is about to be replaced. The editor also keeps hold of the file **and** the project it was opened for, so a save lands where it was meant to even if you switched project while it was open.

### Earlier versions

Every write keeps a copy of what it replaced, so the editor can show them. **Earlier versions** lists the copies of the open file, newest first, with the time each was kept. **See what changed** compares one against what is in the editor right now, line by line, with long identical stretches collapsed. **Put this one back** writes it to the file — an ordinary save, so what it replaces is kept as a version too and nothing is a one-way door. A copy can only be read or put back through the file it was made from: the name it is filed under has to match that file exactly, followed by the time it was taken and nothing else, so a switched-off `.disabled` twin's versions are never offered as the live file's own. For a file that is a link, versions are found under the name the write actually used (the file the link points at), and putting one back writes through the link, which survives — the same thing a switch does. Typing text over a link is still refused, because that content is yours rather than a copy this dashboard made of that same file.

Every write to a real config file is backed up first (this is what the editor's **Earlier versions** list shows), to `~/.claude-context-dashboard/backups/` (a folder only you can open, since the file names there spell out every path you have edited), timestamped, and the file keeps its original permissions — the temporary file it is written through is created with them from the start, so the contents (including any keys in an MCP server's `env` block) are never briefly readable by other users. Before writing, it takes the backup and then re-checks that the file hasn't changed since it was read (modification time, size and inode), and checks again immediately before the rename that puts the new file in place, so a write that lands during the copy is caught too. If a running Claude Code session wrote to it in the meantime — if a running Claude Code session wrote to it in the meantime, the write is refused with a clear message instead of silently discarding that change. A settings file that is itself a link — pointed into a dotfiles repo, say — is written *through*: the file the link points at is the one that changes, and the link stays a link instead of being replaced by an ordinary file. The link is only followed to a file of the same kind, so a `settings.json` pointing at something that isn't a `.json` file is refused rather than overwritten with JSON. That extension is the *only* check: the link is followed wherever it goes — through further links, into any folder on the machine, your home folder or not. It is a link you made yourself, inside a file the dashboard already lists, so following it is following an instruction you left; but it does mean one of these writes can land outside the places every other write here is confined to. If that isn't what you want, don't point a settings file at it. (The editor is stricter and refuses links outright, because it writes whatever text you typed rather than keys the dashboard generated.) Switching something off by renaming is the exception to all of this: it isn't backed up, because nothing is overwritten — the file keeps its content under the other name.

Each copy is named after the full path of its file with `%` and every character a file name should not hold (separators, a drive colon, line breaks) written as `%XX`, then the time, then `.bak`. That reads back to exactly one path, so two files can never share versions. Earlier releases wrote `/` as `__`, which did not read back (`/p/a/b/CLAUDE.md` and `/p/a__b/CLAUDE.md` shared copies, and putting one back could write the other file's text); those old copies are still in the folder. Listing a file's versions renames the old-style copies of it to the new form **when exactly one file on disk could own that old name** — which makes the listing, a GET, change the backup folder. When two files could own it, neither is shown the copies: they stay under their old names, are kept and pruned like any others, and can be opened by hand. A file that no longer exists claims nothing, so its old copies wait until it is back.

Putting a version back is **byte-exact**: the copy's bytes are written as they are, with no decoding in between (a file that was not valid UTF-8 comes back the same). Only a `.json` target is also checked to be valid JSON first.

The copies do not pile up for ever: after each write the folder is trimmed to **at most 20 copies of any one file and 50 MB in total**, oldest first within each file. When the 50 MB total is what is exceeded, space is taken back from whichever file is using the most first, so one large `~/.claude.json` cannot wipe every other file's history. The newest copy of a file is never removed, whatever the total — it is the one an undo needs. This matters more than it sounds: `~/.claude.json` can be several megabytes, so every switch you flip copies all of it.

## Safety and security notes

- **The server only listens on `127.0.0.1`** — it is not reachable from other devices on your network, only from this machine.
- **Every API request is checked** for a matching `Host`/`Origin`, and state-changing ones additionally for a JSON content type, so another website open in your browser can neither read your settings (keys included) nor drive the toggles behind your back. The `Host` check is also what stops a DNS-rebinding attack.
- **Request bodies are capped at 8 MB (8,388,608 bytes)**, so a local program can't make the server accumulate data until it runs out of memory. The count is of bytes as received, and the body is decoded as UTF-8 once, whole, so a multi-byte character cannot be damaged by landing on a chunk boundary. Any real edit is far below the cap.
- **This is not a sandbox for other programs on your machine.** Any local program that can talk to the server can change config for any project on it — but a program running as you could already write those files directly, so that isn't a new privilege. The checks above are about the browser, which otherwise could.
- **Toggling a skill/subagent file is restricted** to the known skill/agent folders (global or the current project's `.claude/skills` or `.claude/agents`) and never overwrites an existing file — it's a no-op if the file is already in the requested state.
- The dashboard reads real settings files, including any API keys or tokens inside an MCP server's `env` block, and displays them. That's inherent to what it's for — keep it to loopback-only use as shipped, and don't run it on a shared machine you don't trust other local users on.

## Known limitations

- This is a static, before-you-start report. It doesn't track live token usage during a running session (Claude Code's own `/context` command does that).
- A change takes effect in the **next** Claude Code session you start; one that is already running keeps whatever it loaded at startup.
- Enterprise-managed settings (deployed by an organization) are not scanned. The page says so, and says whether such a file exists on this machine, in **What this looked at**.
- Nested instructions files are only found one folder deep inside the project. Also called out in **What this looked at**.
- The "did this file change while I had it open?" check compares modification time, size and inode, so a change that keeps all three the same (same length, timestamp put back, same file) would go unnoticed.
- Values set in a personal `settings.local.json` can be seen but not switched — the dashboard's switches write the shared files, so those have to be edited directly.
- The frontmatter parser handles YAML plain scalars and block scalars (`|`/`>`, any chomping indicator) but not list-valued fields — a `description` written as a YAML list (rather than a string) won't show up.

## Updating while it runs

If you update the tool while a dashboard is already running, that dashboard keeps the code it started with while serving you the new page — so the page says at the top that it is talking to an older server, rather than failing with something cryptic, and offers a button that starts it again for you: the running dashboard hands the port to a fresh copy of itself started from the same command line, and the page waits for that one to answer before reloading. It stays attached to the terminal you launched it from, so its output still goes there and one Ctrl+C still stops it.
